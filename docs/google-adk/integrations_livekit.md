# LiveKit runner for ADK[¶](#livekit-runner-for-adk "Permanent link")

Supported in ADKPython v2.9.0Experimental

ADK provides the `LiveKitRunner` class to allow you to serve your live agents over [LiveKit](https://livekit.io/), an open source platform for WebRTC and SIP telephony. This integration acts as a transport adapter that handles audio and video capture, playback, barge-in, captions, and call control, so your ADK agent can become reachable from a browser, a phone, or a game client without any change to the agent.

## Use cases[¶](#use-cases "Permanent link")

You can use LiveKit in a variety of use cases, including browser apps, mobile apps, SIP phone calls, games and immersive clients.

### Browser and mobile apps[¶](#browser-and-mobile-apps "Permanent link")

The agent joins a room as an ordinary participant, so any LiveKit client SDK can talk to it. The connector publishes captions and speaking state on the channels LiveKit's own components bind to, so those components work against an ADK agent without extra wiring:

LiveKit resource

What an ADK agent gets

[Client SDKs](https://docs.livekit.io/transport/)

Browser, Swift, Android, Flutter, React Native, Unity, C++, Rust, and ESP32

[UI components](https://github.com/orgs/livekit/repositories?q=components)

Prebuilt voice-assistant widgets for React, SwiftUI, Compose, and Flutter

[Starter apps](https://github.com/livekit-examples)

Working apps per platform, plus the Agents Playground for talking to an agent with no front end at all

### Phone calls[¶](#phone-calls "Permanent link")

A SIP caller is an ordinary LiveKit participant, so a phone call reaches the agent once an [inbound trunk](https://docs.livekit.io/telephony/accepting-calls/inbound-trunk/) and a [dispatch rule](https://docs.livekit.io/telephony/accepting-calls/dispatch-rule/) point at your worker.

Caller identity lands in ADK session state before the caller speaks, so a function tool reads it like any other state value:

`[](#__codelineno-0-1)from google.adk.tools.tool_context import ToolContext [](#__codelineno-0-2)[](#__codelineno-0-3)async def greet_by_account(tool_context: ToolContext) -> str:   [](#__codelineno-0-4)  """Looks the caller up before greeting them."""  [](#__codelineno-0-5)  number = tool_context.state.get("livekit_caller_phone_number")  # '+15105550100'  [](#__codelineno-0-6)  if not number:    [](#__codelineno-0-7)    return "I could not see the number you are calling from."  [](#__codelineno-0-8)  return await crm.lookup(number)  # your own customer lookup`

The connector buffers keypad entry into a single turn, so a six-digit account number arrives as one input instead of six interruptions.

### Games and immersive clients[¶](#games-and-immersive-clients "Permanent link")

LiveKit's [Unity SDK](https://github.com/livekit/client-sdk-unity) adds real-time audio, video, and data channels to a Unity app, backed by LiveKit Cloud or a server you host. Put an ADK agent in the room and a player can hold a conversation with a character that also acts on the world, such as a voice-driven NPC or an in-game assistant:

`[](#__codelineno-1-1)from google.adk.integrations.livekit import current_call [](#__codelineno-1-2)from google.adk.tools.tool_context import ToolContext [](#__codelineno-1-3)[](#__codelineno-1-4)async def open_the_door(door_id: str, tool_context: ToolContext) -> str:   [](#__codelineno-1-5)  """Opens a door in the game world."""  [](#__codelineno-1-6)  call = current_call(tool_context)  [](#__codelineno-1-7)  return await call.perform_rpc(method="open_door", payload=door_id)`

Whatever the client returns becomes the tool result the model narrates, so the agent describes what actually happened. On the Unity client, register one RPC method; ADK manages the conversation, the tool calls, and the session.

## Get started[¶](#get-started "Permanent link")

-   [ADK](https://adk.dev) >= 2.9.0 with the `livekit` extra.
-   Credentials for a [live model](../../live/models/).
-   A LiveKit server, self-hosted or on LiveKit Cloud. Both expose the same API, so the same worker code runs against either. For local development, run `livekit-server --dev`.
-   `LIVEKIT_URL`, `LIVEKIT_API_KEY`, and `LIVEKIT_API_SECRET` set in the environment.

`[](#__codelineno-2-1)pip install "google-adk[livekit]" "livekit-agents>=1.4"`

Start from the agent you already have. Adding `LiveKitToolset()` gives it call controls such as hanging up or transferring a caller. The toolset activates only when there is a call, so `adk web` still runs the agent unchanged:

`[](#__codelineno-3-1)from google.adk.agents import Agent [](#__codelineno-3-2)from google.adk.integrations.livekit import LiveKitToolset [](#__codelineno-3-3)from google.adk.runners import InMemoryRunner [](#__codelineno-3-4)[](#__codelineno-3-5)root_agent = Agent(     [](#__codelineno-3-6)    model="gemini-live-2.5-flash-native-audio",    [](#__codelineno-3-7)    name="support_agent",    [](#__codelineno-3-8)    instruction="You help customers troubleshoot their home internet.",    [](#__codelineno-3-9)    tools=[check_line_status, LiveKitToolset()],  # check_line_status is your own tool [](#__codelineno-3-10)) [](#__codelineno-3-11)runner = InMemoryRunner(agent=root_agent, app_name="support")`

To connect the agent, pass the runner a connected room. In production you run a worker, which LiveKit dispatches once per call, and the same code serves a browser and a phone.

`[](#__codelineno-4-1)from google.adk.integrations.livekit import LiveKitRunner [](#__codelineno-4-2)from livekit.agents import AgentServer [](#__codelineno-4-3)from livekit.agents import cli [](#__codelineno-4-4)from livekit.agents import JobContext [](#__codelineno-4-5)[](#__codelineno-4-6)server = AgentServer() [](#__codelineno-4-7) [](#__codelineno-4-8)[](#__codelineno-4-9)@server.rtc_session(agent_name="support") [](#__codelineno-4-10)async def entrypoint(ctx: JobContext) -> None:   [](#__codelineno-4-11)  """Bridges one dispatched call into the ADK agent."""  [](#__codelineno-4-12)  await ctx.connect()  [](#__codelineno-4-13)  # LiveKit has no ADK user or session ids. The sample reads them from job metadata.  [](#__codelineno-4-14)  await LiveKitRunner(      [](#__codelineno-4-15)      runner=runner, room=ctx.room, user_id="live-user", session_id=ctx.room.name  [](#__codelineno-4-16)  ).start() [](#__codelineno-4-17) [](#__codelineno-4-18)[](#__codelineno-4-19)if __name__ == "__main__":   [](#__codelineno-4-20)  cli.run_app(server)`

## Deploy the worker[¶](#deploy-the-worker "Permanent link")

The worker dials out to the LiveKit server and receives dispatched jobs over that same connection, so it needs outbound network access, no public address, and no load balancer. Otherwise it is a normal ADK container and deploys the way any ADK agent does. Point the entrypoint at your worker module:

`[](#__codelineno-5-1)CMD ["python", "-m", "support_agent.livekit_worker", "start"]`

[Agents CLI](../../get-started/agents-cli/) deploys that container to Agent Runtime, Cloud Run, or GKE from the `deployment_target` in your `pyproject.toml`. See [Deploy with Agents CLI](../../deploy/agent-runtime/agents-cli/), or deploy by hand to [Cloud Run](../../deploy/cloud-run/) or [GKE](../../deploy/gke/).

Cloud Run probes `$PORT`, while the worker serves its health endpoint on a fixed port, so make the two match. Read the port from the environment when you create the server:

`[](#__codelineno-6-1)import os [](#__codelineno-6-2)[](#__codelineno-6-3)server = AgentServer(port=int(os.environ["PORT"]))`

Deploying with `--port=8081` does the same job, since that is the port the worker uses in production. The worker also sits idle between calls, so run with `--no-cpu-throttling` and `--min-instances=1` to keep it accepting dispatch.

Each dispatched job runs in its own process, so use a durable [session service](../../sessions/). The `InMemoryRunner` class persists nothing between calls.
