# Evaluation for live agents[¶](#evaluation-for-live-agents "Permanent link")

Supported in ADKPython v2.6.0

You can evaluate a live agent the way it actually gets used: a simulated user speaks its turns as audio, your agent answers over a real bidirectional session, and you score what it said back. The eval sets, criteria, and `adk eval` loop are the same ones you already use for text agents, covered in [Evaluate agents](../../evaluate/).

## Drive the agent with speech[¶](#drive-the-agent-with-speech "Permanent link")

The `llm_audio` user simulator synthesizes each simulated user turn with a text-to-speech model and streams it to your agent as audio. That runs the path your users take end to end: speech in, voice activity detection, turn-taking, speech out, transcription. Feeding text to a voice agent skips all of it.

`[](#__codelineno-0-1){   [](#__codelineno-0-2)  "user_simulator_config": {    [](#__codelineno-0-3)    "type": "llm_audio",    [](#__codelineno-0-4)    "model": "gemini-3.7-flash",    [](#__codelineno-0-5)    "max_allowed_invocations": 10,    [](#__codelineno-0-6)    "audio_model": "gemini-3.1-flash-tts-preview",    [](#__codelineno-0-7)    "audio_model_configuration": {      [](#__codelineno-0-8)      "response_modalities": ["AUDIO"],      [](#__codelineno-0-9)      "speech_config": {        [](#__codelineno-0-10)        "voice_config": {          [](#__codelineno-0-11)          "prebuilt_voice_config": { "voice_name": "Kore" }        [](#__codelineno-0-12)        },        [](#__codelineno-0-13)        "language_code": "en-US"      [](#__codelineno-0-14)      }    [](#__codelineno-0-15)    }  [](#__codelineno-0-16)  } [](#__codelineno-0-17)}`

Two models do different jobs here. `model` decides what the simulated user says next, and `audio_model` turns that into speech. Changing `voice_name` and `language_code` is how you test the agent against different voices and accents, which is the kind of regression a text eval cannot catch.

Your eval cases stay as they are. The same conversation scenario or fixed conversation drives a text run or a voice run, so you can reuse a suite you already have. For the full schema, personas, and how to write scenarios, see [Audio user simulation](../../evaluate/user-sim/#audio-user-simulation-for-live-agents).

## Score with rubrics[¶](#score-with-rubrics "Permanent link")

A spoken reply is right in dozens of different phrasings, so criteria that compare against a reference string will fail correct answers. Rubric-based judges let you write the intent in natural language once and apply it across every conversation in the suite:

Criterion

Scores

[`rubric_based_final_response_quality_v1`](../../evaluate/criteria/#rubric_based_final_response_quality_v1)

A single turn's reply

[`rubric_based_tool_use_quality_v1`](../../evaluate/criteria/#rubric_based_tool_use_quality_v1)

Whether tools were called correctly

[`rubric_based_multi_turn_trajectory_quality_v1`](../../evaluate/criteria/#rubric_based_multi_turn_trajectory_quality_v1)

The conversation end to end

`[](#__codelineno-1-1){   [](#__codelineno-1-2)  "criteria": {    [](#__codelineno-1-3)    "rubric_based_multi_turn_trajectory_quality_v1": {      [](#__codelineno-1-4)      "threshold": 0.7,      [](#__codelineno-1-5)      "judge_model_options": { "judge_model": "gemini-3.7-flash" },      [](#__codelineno-1-6)      "rubrics": [        [](#__codelineno-1-7)        {          [](#__codelineno-1-8)          "rubric_id": "verifies_identity_first",          [](#__codelineno-1-9)          "rubric_content": {            [](#__codelineno-1-10)            "text_property": "Across the call, the agent confirms the caller's name and validates their date of birth before disclosing any appointment details."          [](#__codelineno-1-11)          }        [](#__codelineno-1-12)        }      [](#__codelineno-1-13)      ]    [](#__codelineno-1-14)    }  [](#__codelineno-1-15)  } [](#__codelineno-1-16)}`

Reach for the trajectory criterion with [workflows](../workflows/), where what matters is that the agents ran in order and handed off cleanly rather than what any single turn said. Where the answer is genuinely fixed, [`tool_trajectory_avg_score`](../../evaluate/criteria/#tool_trajectory_avg_score) still checks the exact sequence of tool calls and ignores phrasing entirely.

## Run an eval[¶](#run-an-eval "Permanent link")

Add a `live_model_config` block to `test_config.json`. It is what puts the eval in live mode, and it is required for [Live models](../models/#live-models), which are not served over the unary `generateContent` endpoint that text evals use:

`[](#__codelineno-2-1){   [](#__codelineno-2-2)  "live_model_config": {    [](#__codelineno-2-3)    "timeout_seconds": 300  [](#__codelineno-2-4)  } [](#__codelineno-2-5)}`

`timeout_seconds` (default 300) caps how long ADK waits for a turn to finish. Raise it if your agent narrates long tool calls, lower it to fail a stuck session faster.

`[](#__codelineno-3-1)adk eval path/to/your_agent \   [](#__codelineno-3-2)  path/to/your_agent/live.evalset.json \  [](#__codelineno-3-3)  --config_file_path path/to/your_agent/test_config.json`

This needs the eval extras (`pip install "google-adk[eval]"`) and credentials for the Live API and the TTS model. The same run is available through `AgentEvaluator`, which is how you put voice evals in CI.

In `adk web`, the eval dialog has a **Standard | Live** toggle that exposes the input modality and the simulated user's voice and language. When the run finishes, ADK reassembles the audio into a transcript with a playable clip on every turn, so you can hear how the agent sounded instead of only reading what it said.

## Sample[¶](#sample "Permanent link")

The [`workflow` sample](https://github.com/google/adk-python/tree/main/contributing/samples/live/workflow) is a complete voice eval you can run: three live agents in a graph workflow, a tool call in the middle, and an eval set and `test_config.json` wired up with all three rubric criteria.
