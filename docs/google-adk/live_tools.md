# Tools for live agents[¶](#tools-for-live-agents "Permanent link")

Supported in ADKPython v0.1.0Java v0.2.0

Tools work in a live agent much as they do anywhere else in ADK: you pass functions to an agent and the model calls them. How you write a tool does not change under a live connection, so tool definitions, tool context, callbacks, and authentication all follow [Custom Tools](../../tools-custom/).

A live connection adds two capabilities on top. ADK executes tool calls for you inside the `run_live()` loop, so you never write the function-call plumbing the raw Live API would require. Live agents can also use *streaming tools*: functions that stay running and push intermediate results back to the agent, so the agent can react to a stock price moving or a person appearing in a video frame without the user asking again.

## Automatic tool execution[¶](#automatic-tool-execution "Permanent link")

Define tools on your agent and ADK calls them for you inside the `run_live()` loop: it detects the model's function calls, runs the tools (in parallel, with your before/after callbacks), formats the responses, and yields both the call and the response as events. You write the function, not the plumbing.

`[](#__codelineno-0-1)import os [](#__codelineno-0-2)from google.adk.agents import Agent [](#__codelineno-0-3)from google.adk.tools import google_search [](#__codelineno-0-4)[](#__codelineno-0-5)agent = Agent(     [](#__codelineno-0-6)    name="google_search_agent",    [](#__codelineno-0-7)    model=os.getenv("DEMO_AGENT_MODEL", "gemini-live-2.5-flash-native-audio"),    [](#__codelineno-0-8)    tools=[google_search],    [](#__codelineno-0-9)    instruction="You are a helpful assistant that can search the web.", [](#__codelineno-0-10))`

You observe tool activity through the event stream; you never drive it:

`[](#__codelineno-1-1)async for event in runner.run_live(...):     [](#__codelineno-1-2)    if event.get_function_calls():        [](#__codelineno-1-3)        print(f"Model calling: {event.get_function_calls()[0].name}")    [](#__codelineno-1-4)    if event.get_function_responses():        [](#__codelineno-1-5)        print(f"Tool result: {event.get_function_responses()[0].response}")`

## Keeping the agent responsive[¶](#keeping-the-agent-responsive "Permanent link")

A slow tool is survivable in a chat window, where the user watches a spinner. In a live voice conversation it is not: if the agent calls a ten-second API and goes silent, the user assumes the call dropped. You need a tool that does not block the conversation while it runs. ADK gives you two ways to do that, plus plain blocking for the fast case:

Your situation

Use

How

Tool returns in under a second

**Blocking** (the default)

A normal `return` tool

Long wait with nothing to narrate

**[Non-blocking tool](#non-blocking-tools)**

Set `response_scheduling` on the tool

Long wait worth narrating

**[Streaming tool](#streaming-tools)**

`yield` progress from an async generator

## Non-blocking tools[¶](#non-blocking-tools "Permanent link")

Some waits have nothing worth narrating: a long analytics query, a batch export, a media generation job. Progress updates the user did not ask for interrupt the conversation for no benefit. Keep your plain `return`\-once tool and set `response_scheduling` to move it to the background:

`[](#__codelineno-2-1)from google.adk.tools import FunctionTool [](#__codelineno-2-2)from google.genai import types [](#__codelineno-2-3)[](#__codelineno-2-4)async def export_report(region: str) -> dict:     [](#__codelineno-2-5)    """Generate and store the quarterly report. Returns when the export finishes."""    [](#__codelineno-2-6)    await run_export(region)  # a long, plain return-once operation    [](#__codelineno-2-7)    return {"status": "done", "region": region} [](#__codelineno-2-8)[](#__codelineno-2-9)report_tool = FunctionTool(export_report) [](#__codelineno-2-10)report_tool.response_scheduling = types.FunctionResponseScheduling.WHEN_IDLE`

The agent stays free while the tool runs, answers whatever else the user brings up, and folds the result in when it is ready. A runnable example ships as the [`non_blocking_tool_agent` sample](https://github.com/google/adk-python/tree/main/contributing/samples/live/non_blocking_tool_agent).

Requires ADK Python 2.4 or higher

The `response_scheduling` feature was added in adk-python 2.4, and support is per model. See [Supported models](../models/#live-models).

`response_scheduling` also controls *when* a finished result reaches the user:

Value

Behavior

Use it for

`WHEN_IDLE`

Waits for a natural pause

Reports and lookups, the usual choice

`INTERRUPT`

Delivers immediately

Alarms, failures, "the transfer failed"

`SILENT`

Enters context, announced only if relevant

Background info the model may use later

## Streaming tools[¶](#streaming-tools "Permanent link")

A streaming tool stays running and pushes intermediate results back to the agent, so the agent can narrate progress or react to a changing input (a stock price, a person entering a video frame) without the user asking again. Making a tool stream is a one-line change: an `async` function that `yield`s instead of `return`s. ADK treats any async-generator tool as non-blocking automatically.

`[](#__codelineno-3-1)import asyncio [](#__codelineno-3-2)from typing import AsyncGenerator [](#__codelineno-3-3)[](#__codelineno-3-4)async def query_sales_database(region: str) -> AsyncGenerator[str, None]:     [](#__codelineno-3-5)    """Run the quarterly sales report. Call this once; it streams its own updates."""    [](#__codelineno-3-6)    yield "Connecting to the warehouse..."    [](#__codelineno-3-7)    await asyncio.sleep(4)    [](#__codelineno-3-8)    yield "Aggregating by product line..."    [](#__codelineno-3-9)    await asyncio.sleep(4)    [](#__codelineno-3-10)    yield f"Done. {summarise(region)}"`

Pass it to `tools=[...]` like any other tool. The model gets each `yield` as a live update, so instead of silence the user hears "let me pull those up... still aggregating... got it: EMEA did $4.81M, up 12.4%." This suits RAG pipelines, multi-stage aggregation, and build-and-test runs, anywhere the progress is worth telling.

Add ADK's reserved `stop_streaming` tool (an empty function ADK intercepts by name) so users can cancel: "never mind, cancel that."

### Video streaming tools[¶](#video-streaming-tools "Permanent link")

Add an `input_stream: LiveRequestQueue` parameter and ADK feeds the user's realtime input into a dedicated queue for that tool, so it can pull video frames and react to them.

Requirements for any streaming tool:

-   It must be an `async` function typed to return an `AsyncGenerator[T, None]`, where `T` is the type you `yield`.
-   For video, add `input_stream: LiveRequestQueue`; ADK fills it in.

The pattern below drains the queue to the newest frame, discarding stale ones, and yields only when the answer changes so the agent stays quiet otherwise.

## Tool execution context[¶](#tool-execution-context "Permanent link")

A tool or callback receives an `InvocationContext` for state, history, and artifacts. It works the same as in any ADK agent — see [Agent context](../../context/) — with one difference that matters live: **one `InvocationContext` spans the entire `run_live()` loop**, created when you call `run_live()` and living across every agent and every turn until the session ends. In a request/response agent an invocation is a single turn; in a live session it is the whole conversation.

Two fields come up most in live tools:

Field

What it gives you

`context.run_config`

The session's [configuration](../configuration/) — response modalities, transcription, limits

`context.end_invocation`

Set to `True` to terminate the whole streaming session immediately
